# Cloudflare 1102 FC27 audit

Date: 2026-09-15

## Root cause

The repository contains a direct resource-limit risk on the crawled entity
routes, including `/fc27/clubs/:slug`. Before this change,
`fetchEntityPlayers()` called `getAllPlayersStatic()`. A cold Worker isolate
therefore read the manifest plus every player-detail shard (about 162 asset
subrequests for the current 20,689-player dataset) before filtering one club.
The source itself describes this as an all-shard fan-out and caps it at eight
concurrent requests. It still creates a large amount of JSON parsing, array
allocation and repeated ASSETS binding work for a single public request. This
is consistent with Worker CPU/subrequest exhaustion under crawler load and is
the repository-backed cause found for the reported club-route failures.

There is no local Cloudflare request log, so the reported Ray ID cannot be
attributed to a specific invocation from this checkout. Player detail routes
do **not** use this all-shard path: they read `players/index.json` and one
detail shard. They nevertheless incurred an unnecessary auth/session lookup
in middleware on every request.

## Request architecture

`GET /fc27/clubs/walsall` reaches the Cloudflare Worker generated by
OpenNext (`.open-next/worker.js`, configured as `main` in `wrangler.jsonc`).
The Worker runs Next middleware, resolves the App Router page
`src/app/fc27/clubs/[slug]/page.tsx`, then `renderDetailPage()` and
`fetchEntityPlayers()`. FC27 public data is served from the `ASSETS` binding:
the manifest selects a versioned artifact under `public/fc27-data`, and the
response is server-rendered with metadata and JSON-LD.

`GET /fc27/players/78050-david-de-ornelas` follows the same Worker/App Router
path. It resolves the leading numeric ID, reads the player index and one
player shard, renders server-side metadata/canonical/JSON-LD, then returns
HTML. It does not query D1. A Supabase/PostgREST fallback exists only if a
static artifact is unavailable.

Cloudflare bindings in versioned configuration are: Worker assets,
`WORKER_SELF_REFERENCE`, D1 `ANALYTICS_DB`, and KV
`ANALYTICS_RATE_LIMIT`. No R2, Durable Object, or FC27 D1 binding is present.

## Why Cloudflare showed `Cache status: None`

The routes are generated dynamically through the OpenNext Worker. No
versioned Cloudflare Cache Rule or Worker Cache API implementation makes these
HTML responses cache-eligible by default. The previous middleware also ran
Supabase/Clerk auth handling for public pages, which can refresh cookies and
makes shared caching unsafe. Existing cache headers covered only `/browser/*`
and sitemap XML, not FC27 HTML.

## Changes made

- `src/lib/fc27/entities.ts`: entity detail pages now filter the complete,
  single-file `search/index.json` instead of loading all player detail shards.
  The index already contains all fields displayed by ranking cards. This
  changes the normal club/nation/league detail request from roughly 160 shard
  reads to one index artifact read.
- `src/middleware.ts`: player and club FC27 pages bypass the session refresh
  path. API, `/app`, admin, auth and all other routes retain normal auth
  middleware behavior.
- `next.config.ts`: only `/fc27/players/:path*` and `/fc27/clubs/:path*`
  advertise `Cache-Control: public, max-age=60, s-maxage=3600,
  stale-while-revalidate=86400`. This does not grant cacheability to API or
  authenticated routes.

## Cache strategy and required Cloudflare Dashboard action

After deploying this commit, create one Cache Rule with all of:

1. method is `GET` or `HEAD`;
2. URI path starts with `/fc27/players/` **or** `/fc27/clubs/`;
3. cache eligibility is enabled and origin cache-control is respected;
4. cache key includes the full query string (do not normalize it away);
5. bypass cache when the request contains a session/auth cookie, as a
   defence-in-depth guard.

Do not use a domain-wide Cache Everything rule. Do not include `/api/*`,
`/app/*`, admin/auth paths, requests with mutations, analytics, or personalized
content. Purge these two path prefixes after each FC27 dataset deployment;
the one-hour edge TTL and one-day stale window otherwise limit staleness.

## SEO and crawler impact

The routes remain server-rendered and retain their canonical metadata and
JSON-LD. `robots.ts` allows crawling and publishes sitemap URLs. Sitemap
index/chunk handlers already return a one-day shared cache directive. No
verified bot was blocked or special-cased. A future anti-scraping rule, if
needed after observing cache-hit and Worker CPU metrics, should rate-limit
unverified clients by IP plus FC27 path while allowing verified bots; it should
not be based on country or blanket ASN/browser blocking.

## Residual risks

Other FC27 tools (`rankings`, `stat-finder`, `hidden-gems`, and similar-player
calculation) still intentionally use the all-detail-shard aggregate and can
be expensive when uncached. They were outside the observed player/club path
and are not changed in this minimal fix. Monitor Worker CPU and subrequests
by route after deployment; if 1102 persists on a different path, inspect that
route rather than expanding this cache rule.
